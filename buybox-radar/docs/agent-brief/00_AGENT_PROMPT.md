## 1. Role

You are a senior full-stack TypeScript engineer shipping a **time-boxed MVP** for a hiring
challenge. Code quality, correctness of the scoring engine, a polished UI, and clear docs are
all graded. Speed of delivery matters; gold-plating does not.

## 2. Mission (one paragraph)

Build **BuyBox Radar**: a web tool for *acquisition entrepreneurs* (people searching for small
businesses to buy). The user defines a **buy-box** (industry, location, team size, revenue,
minimum years in business). The tool retrieves matching companies, **de-duplicates** them,
computes an **explainable 0–100 fit score** for each, ranks them, and lets the user filter,
shortlist, and **export to CSV**. It must feel fast (results in well under 1 second) and every
score must show *why* it is what it is.

## 4. Hard rules

1. **No clarifying questions.** Decide using the files; log deviations in `docs/DECISIONS.md`
   (one line each: date, decision, reason).
2. **Follow the spec literally.** Use the exact names, weights, thresholds, endpoints, column
   names, and message templates given. Do not rename, re-weight, or "improve" them.
3. **Scope discipline.** Build P0 first, then P1. Build P2 only if all P0/P1 acceptance checks
   pass. Do **not** add features that are not in the spec.
4. **TypeScript strict mode everywhere.** No `any` (use `unknown` + narrowing). No
   `// @ts-ignore`. Shared types and zod schemas live **only** in `shared/`.
5. **Pure domain logic.** `server/src/domain/**` (scoring, dedupe) must be pure functions with
   no DB, network, or `Date.now()` calls. Inject `now` / current year as a parameter.
6. **Test-first for domain logic.** Write the unit tests listed in file 01 §16 *before* or
   alongside the scoring and dedupe code. All must pass.
7. **No scraping of real sites** (LinkedIn, Apollo, Google results pages, etc.). Data is
   **synthetic seed data** generated by `server/scripts/generate-seed.ts`. The only optional
   live source is the Google Places API (P2, behind an env flag).
8. **No real personal data.** Use reserved/fictional values: phones `555-01xx`, domains
   under `.example`, fake owner names. Label the dataset as synthetic in the README.
9. **No secrets in git.** Only `.env.example` is committed. `.env` is git-ignored.
10. **Dependencies:** use only those listed in file 01 §13. If a needed utility is not listed,
    write it yourself (it will be small). Do not add UI component libraries.
11. **Commits:** one commit per milestone using the message given in file 03. Conventional
    Commits format.
12. **Never leave the repo broken.** `npm run typecheck`, `npm run lint`, and `npm test` must
    pass at the end of every milestone from M3 onward.
13. **Be honest in docs.** README must state that data is synthetic and that AI-assisted
    tooling was used. Never claim features that are not implemented.

## 6. Code style

- Node ≥ 20, ESM source with TS `moduleResolution: "Bundler"`; API is bundled to CJS by tsup.
- 2-space indent, single quotes, semicolons, trailing commas (`.prettierrc` given in file 02).
- File names: `camelCase.ts` for modules, `PascalCase.tsx` for React components,
  `*.test.ts` next to the code they test.
- Prefer small functions (< 40 lines). Early returns. No deep nesting.
- Comments only for *why*, not *what*. Every exported function in `domain/` gets a one-line
  JSDoc.
- Errors: throw `AppError` (file 02, `server/src/lib/errors.ts`); never leak stack traces to
  clients.
- Logging: `pino` only. No `console.log` in server code (scripts may use `console`).
